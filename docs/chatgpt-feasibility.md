# ChatGPT extraction feasibility — M2.5

Assessment date: **2026-10-19**. Recommendation: **conditionally feasible for unattended ChatGPT Work operation; not yet verified on this account/integration**. Interactive protocol integration is implemented and locally testable. Do not depend on unattended extraction in the production architecture until the acceptance test below passes.

Do not conflate every product called “Tasks”: the recommendation above is scoped to the current documented **ChatGPT Work** scheduling surface. Legacy custom GPT/Actions flows and workspace agents are different mechanisms. If the actual UI cannot attach the custom plugin to a scheduled run, that surface cannot perform this workflow; do not replace the missing integration with a prompt containing credentials or a public raw-mail endpoint.

## Preferred mechanism

Connect the isolated Worker as a custom OAuth-authenticated MCP server. Its two tools map to the required REST endpoints, and share their validation/authorization/commit logic. No model inference API is called from Cloudflare. Extraction would occur in the user's ChatGPT session/task, subject to plan limits and policy. This design adds no separately billed LLM API call, but does not promise unlimited/included execution or zero Cloudflare/auth-provider costs.

The checked-in OpenAPI uses reserved `.invalid` hosts, not the public demo. Its GET allocation and POST write are marked consequential for an Actions client. That intentionally prevents claiming an approval-free Actions schedule from this definition. MCP declares both tools as writes because GET allocates claims; this may also require approval depending on host policy.

## Unsupported assumptions and blockers

- Unsupported by the authenticated MCP contract: pasting a bespoke shared API key into an MCP prompt, using an unauthenticated server for private data, or substituting a machine-to-machine grant for the documented user OAuth flow.
- Not established: this user's plan/UI supports custom MCP creation and scheduled plugins, token refresh persists across scheduled runs, or private submissions complete without per-run approval. Test all of these; do not label them successful from local mocks.
- Not performed: live HTTPS/tunnel exposure, real OAuth authorization-code/PKCE linking, ChatGPT reasoning/tool selection, model quality/adversarial prompt evaluation, and a scheduled run. The present no-deployment/no-connection boundary blocks those tests.
- Not implemented as production features: general MIME-to-safe-text parsing, real-message export, credential/token issuance, publication permission, semantic deduplication, or publication. M3/M4 remain responsible for independent downstream gates.

## Test status and acceptance decision

| Test                            | Status                                                                     | Required evidence                                                                                                                        |
| ------------------------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Local REST/resource JWT checks  | Automated local tests                                                      | Scope/issuer/audience/subject/client/time checks; stable bounded batches; no private leakage                                             |
| Local SDK MCP round trip        | Automated local workerd rehearsal                                          | initialize → tools/list → retrieve fixtures → submit deterministic test JSON → identical replay; no opportunities written                |
| Interactive ChatGPT extraction  | **NOT RUN — blocked by connection/exposure authorization and OAuth setup** | ChatGPT trace plus matching private batch/submission receipt; all three fixture outcomes checked                                         |
| Unattended scheduled extraction | **NOT RUN — same blockers, plus account/approval policy unverified**       | A scheduled run while user is absent authenticates, retrieves, analyzes, submits; no per-run human confirmation; matching stored receipt |

A successful unattended test requires **all** steps, not merely a reminder, draft JSON, read-only retrieval, local SDK script, “Run now” manual interaction, or an unverified task summary. Record model/host/date, task/run identifier, authentication/refresh events, selected tools, approval prompts and D1 receipt IDs without credentials. Use only synthetic data. Repeat after token expiry to verify refresh. If authentication/approval/tool availability blocks completion, record that blocker and keep the result conditionally feasible (or unsupported on that tested surface/policy).

Follow [the manual test procedure](agent-integration.md). The PoC and its [live-test preparation follow-up](agent-live-test.md) stop before connection and deployment; neither schedules work or requests a token. Source pages are version-sensitive; recheck them before the future test and record any contradictory product-specific documentation instead of assuming interchangeable features.
